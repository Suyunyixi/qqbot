# 群聊需求、工具链与系统研究

研究日期：2026 年 11 月 9 日。此文用于规划和复核，不代表下述建议已经实现。

**后续进展：**原始事件保存与网关游标同事务提交；引用事件自带的图片支持归档与历史回看；工具大结果按会话归档，主对话记录使用框架检查点；模型与搜索的缓存用量已兼容 Anthropic 字段。B 站下载、脚本生成图片及模拟发送链路已在容器中试跑。最近一条实际回合主模型输入约 5.4 万 Token，只有一个样本，尚不足以证明性能或成本问题已解决。真实群里的 @、不同消息格式、素材准确性和工具发现效果仍需持续验证；下文各项为研究时快照。

## 样本与限制

分析范围是本机现有 SQLite 记录：两个群共 202 条入站消息、8 个发送者，另有私聊记录。数据集中在 11 月 4 日至 6 日，11 月 7 日、8 日没有群入站记录，11 月 9 日只有少量记录；中间存在离线缺口。样本包含大量调试、测试和纠错，不能当成稳定的长期兴趣统计。文中不记录群号、用户标识、个人聊天原文或密钥。

工具执行指标的采集始于 11 月 6 日，早期图片制作和搜索行为不能据此统计。指标中的一次主回复记录是一次模型调用，不等同于一个完整 QQ 回合；它不包含群消息排队和 QQ 发送的完整耗时，也不等于最终费用。系统自检请求、部分第三方搜索或失败重试可能不在统计中。

## 真实出现的需求及优先级

| 方向 | 现有证据 | 应达到的体验 | 目前状态 |
| --- | --- | --- | --- |
| 接住群聊与熟人互动 | 多人插话、请机器人询问群友、反复纠正谁说过什么 | 理解当下多人的连续对话，适当 @ 目标，保持大肥鱼的口吻 | 能记录、查历史和发送 @；真实语义、引用和口吻仍需回归验证 |
| 图片与引用 | 让机器人看上面的截图、理解引用；曾多次认错话题 | 正确定位原图和作者，需要时真实读取；缺失时说明 | 图片可归档和回读，但实际附件有 11 条保存、8 条 HTTP 4xx 失败；不是所有格式都已验证 |
| 新鲜游戏资料与攻略 | 明日方舟干员、游戏配队、金铲铲阵容等实际提问 | 区分版本和日期，查来源原文，说明事实与社区观点 | 有搜索和网页读取；准确性、信息时效、游戏资料覆盖未做系统评测 |
| 图片制作与卡片 | 群友要求榜单、人物卡片、明确要求真实素材 | 查证 → 找素材 → 下载 → 自主排版 → 检查产物 → 发图 | 有搜索、下载、Python 及发送工具；模板输出、素材获取和端到端效果仍需真实验收 |
| 视频和文件 | 用户提出 B 站下载及多格式交付；历史有视频榜单查询 | 下载、转换、校验、发送，耗时任务可回调 | 代码具备相关链路，现有采集期缺少真实 B 站端到端执行证据，不应称为已验证 |
| 群内轻互动 | 群友调侃、叫机器人、互相询问 | 简短自然，不把闲聊变成机械的能力说明 | 需要人格一致性和连续群聊评估，而非新增一堆娱乐插件 |
| QQ 原生消息 | 用户反复要求 Markdown、@、卡片 | 按表达需要选择 QQ 原生能力并核对发送结果 | 已有发送实现；一次历史卡片发送报“无 ark 模板权限”，不能把所有卡片说成可用 |

订阅推送、提醒、天气、表情包和群小游戏在其他机器人中常见，但本地样本不足以证明这些群友经常需要，属于备选而非优先结论。语音方案尚待用户提供，不应擅自实施。

## Token 与性能：已测到什么

- 11 月 9 日记录了 11 次主模型调用，平均输入约 37,374 Token；其中两次分别为 82,750 和 96,150 输入 Token。这些是提供商返回的模型调用量，不是两次完整用户回合的总量或费用。
- 同日这 11 次调用平均约 4.0 秒，最长约 9.2 秒；这是单次模型请求时间，不包含排队、其他工具调用和 QQ 发送。样本太少，不能当作系统响应延迟的稳定指标。
- 11 月 6 日有 9 次记忆整理，合计输入 55,511、输出 34,130 Token，平均每次约 23.1 秒。整理异步执行，但仍有模型成本及并发资源开销。
- 只读检查实际检查点时，一个会话累计 19 条 Agent 消息、约 149,220 个文本字符；其中一个 `grep` 返回约 80,070 字符，两个带重复背景的用户消息块各约 16,499 和 17,303 字符。字符数不是 Token；这些检查点也不能单独证明哪一次模型调用的精确组成，但足以证实上下文膨胀风险。
- 当前 [运行逻辑](../src/agent/runtime.ts) 每轮将摘要、相关记忆、会话备注和参与者资料嵌入新的用户消息，持久会话保留旧消息，所以相同资料可能出现多个历史副本；当前资料与旧副本还可能不一致。
- 本项目安装的 Deep Agents 声明中，`grep` 等文件工具被排除在大工具结果自动转存机制外，理由是预期工具自行截断；但实际看到约 8 万字符的结果，说明不能只假设默认机制已经解决。应先查明该结果是否来自单条长行、后端实现或版本行为，再做分页、结果存档与可回查设计，而不是仅靠硬截断。
- 当前指标只保存输入、输出、总 Token 和单次耗时，没有持久化命中缓存、未命中缓存、推理 Token 和真实价格。DeepSeek 返回这些缓存字段，前缀匹配有助于命中，但服务商不保证命中率；因此不能根据总输入 Token 算实际费用或断言缓存已失效。[DeepSeek 缓存文档](https://api-docs.deepseek.com/zh-cn/guides/kv_cache/)

建议把持久对话、单次临时背景和大工具产物分开：保留框架会话及完整原始记录；只在当前调用中注入最新的可变资料，历史工具大结果保存并按需查阅；先做对照测试，避免破坏上下文、引用、图片和跨轮工具协议。固定的系统人格、工具定义尽量稳定，动态资料放在合适位置，以实际缓存命中率而非假设衡量收益。

## Harness 审查

1. **触发与保存**：实际流程是先记录原始入站消息，再判断 @ 或关键词；静默消息不应启动模型。这符合既定目标，但模型使用期间或进程故障的完整性仍需验证。
2. **会话与历史**：当前本地实现已使用同一 LangGraph thread 持续保存会话，同时 SQLite 独立保存原始消息。不要再按每轮清空 thread 或用纯代码强行解释用户意图；首次迁移、摘要边界、任务回调和并发消息要分别测试。
3. **正在生成时插话**：[live-context.ts](../src/agent/live-context.ts) 在模型调用前、模型回复后和实际发送前检查新消息，必要时再次调用模型。它解决的是错过插话，但可能增加调用、排队和成本；应记录触发次数及额外耗时，评估在真实群聊中的收益，避免无关插话导致反复生成。
4. **引用**：[quoted-message.ts](../src/agent/quoted-message.ts) 目前主要读取 `msg_elements`；实际原始事件中也出现 `parallel_message.msg_nodes`。不同结构的引用需要真实样本测试，不能把引用索引直接当数据库消息 ID，也不能无依据地补全发送者。
5. **人格**：主人格来自 SQLite 并在主 Agent 的系统消息中传入，群风格和工具结果作为数据；这保证配置不会被聊天工具直接修改，但不能保证模型每次都表现稳定。应针对普通闲聊、搜索、工具失败、后台回调及群友纠错设计测试，不要用额外模型强制改写每条消息。
6. **恢复**：QQ 会话状态和序号存 SQLite，但目前 SDK 先保存序号、后分发消息，异常退出存在漏存窗口。需先验证网关协议和幂等语义，设计安全的事件持久化、恢复日志和重复事件去重；不能保证平台在长时间离线后补发。
7. **工具发现**：[tool-discovery.ts](../src/agent/tool-discovery.ts) 用中文二字词和名称匹配自动开放最多五项，并允许模型再查目录。它省去了额外分类模型，但同义表达、没有命中时的发现、工具越来越多时的正确率均未实测；还有一些高频工具始终随请求提供。应测定义长度、命中率、漏召回和多轮工具调用，不应只按工具数量断言快慢。
8. **后台任务和交付**：分别核验真实下载、格式转换、产物落盘、发送成功与失败重试；任务完成不等于文件已发送。保留回调给主 Agent 的原始需求、执行结果和任务期间群友补充。

LangChain 将 Deep Agents 定义为包含规划、文件、上下文和子代理的 harness，长上下文支持摘要和文件转存；具体行为仍取决于项目使用的版本与配置。[Deep Agents 官方概览](https://docs.langchain.com/oss/javascript/deepagents/overview)

## 推荐实施顺序与验收

1. **建立真实基线**：管理页按 QQ 回合展示端到端耗时、模型调用次数、工具调用与结果大小、Token 输入/输出/缓存命中/推理、后台任务和交付状态；未知值显示未知。先建立关联 ID 和隐私边界，不默认持久化完整模型提示词。对旧版本指标保留历史局限。
2. **修复会话膨胀**：保持现有持久 thread 和 SQLite 原文；去除历史临时背景的重复注入、让大工具结果可分页或归档回读。用相同的虚构多群对话重放，比较每轮 Token、缓存命中、耗时，同时验证多人接话、引用、历史图片及工具协议。不得为了省钱清空会话或截断关键原文。
3. **对话与多模态回归**：覆盖多人连续发言、只 @、引用旧消息、当前话题与旧图冲突、图片归档失败、任务执行中的纠错、人格和真实 @/Markdown。以准确指代和实际发送结果验收，模型自由表达，不增加一轮通用的强制语义复核。
4. **搜索与图片交付**：挑选游戏版本变动、B 站榜单和人物图片等代表场景，核对来源、时间、素材和最终发送结果。来源受限或素材不可用要明确，不虚构。原生卡片权限按账号实测；图片卡片只在用户需要时生成。
5. **工具扩展机制**：为新增工具声明名称、中文用途、输入输出、执行位置和权限，提供可独立运行的契约测试；不强制为每个工具写死关键词。用实际多样化问法测自动发现、目录查找、执行到交付的成功率与耗时；以可观察结果决定是否继续使用当前轻量匹配或引入别的检索方式。
6. **后续研究**：在实际需求足够后再评估订阅提醒、群工具、个性化偏好和独立采集服务。任何新增自动记忆或偏好推断需可查看、更正、删除，并区分用户明确偏好和系统推测。

## 平台与离线边界

当前两个群的 QQ 机器人消息接收设置经只读接口查询均为 `all`。社区资料提到另一种“@ 时带最近 10 条”模式，但是否能恢复离线消息、其载荷格式及与全量接收的关系，尚未在本账号实测；用户选择暂不切换群设置。普通 QQ 群历史的公开主动拉取接口尚未核实到，不应把某一个路径的 HTTP 405 当作全部接口不存在的证明。运行期间保存消息与离线恢复是不同问题。
